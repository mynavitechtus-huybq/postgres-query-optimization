# Q3 — Doanh thu theo tháng

Tối ưu ở ba tầng khác nhau, đo tách từng tầng.

| | Tầng | Kỹ thuật | Thời gian | So V1 |
|---|---|---|---:|---:|
| V1 | — | không | 134,768 ms | — |
| V2 | access path | partial covering index | 96,267 ms | 1,40× |
| V3 | query | viết lại, bỏ `GROUP BY` trên biểu thức | 28,791 ms | 4,68× |
| V4 | data model | materialized view | 0,040 ms | 3.369× |

Plan: [`V1`](../plans/q3_v1_baseline.txt) · [`V2`](../plans/q3_v2_access_path.txt) · [`V3`](../plans/q3_v3_lateral.txt) · [`V4`](../plans/q3_v4_matview.txt) · [`đã loại`](../plans/q3_alternatives.txt)

Median 5 lần chạy nóng, cùng trạng thái bảng cho mọi phép đo: `orders` 67 MB,
visibility map 8604/8604 all-visible, `work_mem` 4 MB, TimeZone `Etc/UTC`.

Index cần thiết đã có sẵn từ Q1 và planner đã dùng, mà query vẫn chậm hơn cả Q1 lúc
chưa có index nào.

## Bottleneck

```
GroupAggregate  (rows=253033)  (actual rows=25)          <-- lệch 10.000 lần
  -> Sort  (rows=250983)  Sort Method: external merge  Disk: 6152kB
       -> Bitmap Heap Scan  Heap Blocks: exact=8604      <-- đọc gần hết bảng
```

![V1 baseline](../images/q3-v1-baseline.png)

Phân rã: scan ~65 ms (49%), sort ~46 ms (34%), aggregate ~21 ms (16%). Hai vấn đề độc
lập, phải sửa riêng.

**Aggregation.** Ước lượng 253.033 nhóm, thực tế 25. Postgres chỉ thu thập thống kê cho
cột, không cho biểu thức, nên với `GROUP BY date_trunc('month', created_at)` nó đoán số
nhóm xấp xỉ số dòng. Vì tưởng có 253 nghìn nhóm nên nó loại `HashAggregate`, buộc phải
`Sort` đủ 250.983 dòng, vượt `work_mem` 4 MB và đổ ra đĩa.

**I/O.** `created_at >= '2024-01-01'` không lọc bỏ dòng nào vì dữ liệu bắt đầu từ
2024-08-25, nên `WHERE` khớp 25,1% bảng. Index cũ `(status, created_at)` vẫn phải vào
heap lấy cột `total`, đọc đủ 8.604 block.

## V2 — Tầng access path

```sql
CREATE INDEX idx_orders_paid_created_at
    ON orders (created_at)
    INCLUDE (total)
    WHERE status = 'paid';
```

Query giữ nguyên, không đổi schema hay application logic.

`WHERE status = 'paid'` khiến index chỉ chứa ~25% số dòng nên nặng 7744 kB, so với
41 MB của covering index đầy đủ trên `(status, created_at)`. `INCLUDE (total)` đưa nốt
cột cần cộng vào index để có Index Only Scan, xác nhận bằng `Heap Fetches: 0`.

| | V1 | V2 |
|---|---:|---:|
| Buffers (shared) | 9.571 | 968 |
| Heap Fetches | — | 0 |
| Scan | ~65 ms | ~35 ms |
| Sort | external merge 6152 kB | vẫn 6152 kB |
| Ước lượng nhóm | 253.033 vs 25 | vẫn lệch |

![V2 partial covering index](../images/q3-v2-partial-index.png)

![kích thước index](../images/q3-index-size.png)

Đọc ít hơn 9,9 lần mà chỉ nhanh hơn 1,40 lần. V2 chỉ chữa được phần I/O, còn `Sort` và
ước lượng sai vẫn nguyên. Sau V2, sort + aggregate chiếm 60/96 ms — chỗ mà index không
với tới được.

## V3 — Tầng query

Vấn đề gốc là planner không đoán được `GROUP BY date_trunc(...)` sẽ ra bao nhiêu nhóm.
Bỏ luôn cái `GROUP BY` đó: sinh sẵn danh sách mốc tháng rồi với mỗi tháng cộng riêng.

```sql
SELECT m.month, x.revenue
FROM generate_series(
       date_trunc('month', TIMESTAMPTZ '2024-01-01'),
       (SELECT max(created_at) FROM orders),
       interval '1 month') AS m(month)
CROSS JOIN LATERAL (
  SELECT SUM(o.total) AS revenue
  FROM orders o
  WHERE o.status = 'paid'
    AND o.created_at >= m.month
    AND o.created_at <  m.month + interval '1 month'
) x
WHERE x.revenue IS NOT NULL
ORDER BY m.month;
```

`generate_series` sinh các mốc tháng, `CROSS JOIN LATERAL` chạy phần `SUM` một lần cho
mỗi mốc. Không còn gom nhóm trên biểu thức nên không còn chỗ để planner đoán sai.

![V3 viết lại query](../images/q3-v3-lateral.png)

```
Nested Loop  (actual time=0.865..43.791 rows=25 loops=1)
  -> Function Scan on generate_series m  (rows=32 loops=1)
  -> Aggregate  (rows=1 loops=32)
       -> Index Only Scan using idx_orders_paid_created_at  (rows=7843 loops=32)
            Heap Fetches: 0
```

Không còn node `Sort` trên 250.983 dòng, không còn `temp read/written`. Mỗi tháng là một
Index Only Scan trên khoảng liền mạch. `loops=32` vì `generate_series` sinh 32 mốc từ
2024-01, trong đó 7 tháng đầu không có dữ liệu và bị `WHERE x.revenue IS NOT NULL` loại.

Chỉ đổi câu query, dùng lại đúng index của V2, dữ liệu vẫn realtime.

## V4 — Tầng data model

```sql
CREATE MATERIALIZED VIEW monthly_paid_revenue AS
SELECT (date_trunc('month', created_at AT TIME ZONE 'UTC'))::date AS month,
       SUM(total) AS revenue
FROM orders WHERE status = 'paid'
GROUP BY 1;

CREATE UNIQUE INDEX idx_monthly_paid_revenue_month ON monthly_paid_revenue (month);
```

```sql
SELECT month, revenue FROM monthly_paid_revenue
WHERE month >= DATE '2024-01-01' ORDER BY month;
```

250.983 dòng gộp sẵn thành 25 dòng, 40 kB. Không tối ưu đường truy cập nữa mà bỏ hẳn
việc aggregate lúc chạy query.

![V4 materialized view](../images/q3-v4-matview.png)

### Chi phí

| | |
|---|---:|
| Build lần đầu | 108,8 ms |
| `REFRESH` | 57–61 ms |
| Query | 0,040 ms |
| Dung lượng | 40 kB |

![chi phí refresh](../images/q3-refresh-cost.png)

`REFRESH` rẻ hơn một lần chạy query gốc, và cũng dùng partial index của V2.

| Kịch bản | Tổng |
|---|---|
| Refresh 1 lần, đọc 100 lần | 60 + 100×0,04 = 64 ms |
| Refresh 1 lần, đọc 1 lần | 60 ms — ngang V3 |
| Refresh mỗi lần đọc | 60 ms mỗi lần — chậm hơn V3 |

Con số 3.369× chỉ đúng khi đọc nhiều hơn ghi.

V3 đúng ở cả hai múi giờ vì nó vẫn theo TimeZone của session giống query gốc.

V4 chốt `'UTC'` nên chỉ khớp khi session cũng ở UTC. `date_trunc('month', created_at)`
trong query gốc phụ thuộc TimeZone của session, nên cùng một dòng rơi vào tháng khác
nhau tuỳ ai chạy. Cần chốt theo giờ Việt Nam thì đổi trong định nghĩa view rồi refresh
lại.

Cùng họ vấn đề với Q6: `date_trunc(text, timestamptz)` là `STABLE` chứ không `IMMUTABLE`.

| | V2 | V3 | V4 |
|---|---|---|---|
| Thời gian | 96,3 ms | 28,8 ms | 0,040 ms |
| Đổi query | không | có | có |
| Đổi schema | +index 7,7 MB | +index 7,7 MB | +matview 40 kB |
| Thêm việc vận hành | không | không | lịch refresh |
| Dữ liệu | realtime | realtime | cũ theo chu kỳ refresh |
| Múi giờ | theo session | theo session | chốt UTC |

V3 là phương án chính: nhanh 4,68×, không thêm gì để vận hành, realtime, đúng ở mọi múi
giờ, và chỉ cần một câu query viết khác đi cộng index của V2.

V4 giữ lại cho dashboard nếu chấp nhận dữ liệu cũ vài phút.
`REFRESH ... CONCURRENTLY` không khoá đọc (cần UNIQUE index, đã tạo) nhưng chậm hơn
refresh thường.

## Hai phương án đã đo rồi loại

Chi tiết: [`plans/q3_alternatives.txt`](../plans/q3_alternatives.txt)

![ALT-A CREATE STATISTICS](../images/q3-alt-statistics.png)

**`CREATE STATISTICS` — 20,594 ms.** Chữa đúng phần aggregation: ước lượng về 25,
`HashAggregate` được chọn, hết sort và hết đổ đĩa. Nhanh nhất trong các phương án
realtime. Loại vì ràng buộc đề bài, không phải vì kém.

**Cột generated — 33,941 ms.**

```sql
ALTER TABLE orders ADD COLUMN created_month date
  GENERATED ALWAYS AS ((date_trunc('month', created_at AT TIME ZONE 'UTC'))::date) STORED;
```

Biến biểu thức thành cột thật để Postgres thu thập `n_distinct` như cột thường, đo được
đúng 25 mà không cần `CREATE STATISTICS`. Loại vì:

- `ALTER TABLE` rewrite toàn bảng mất 2,2 giây và giữ `ACCESS EXCLUSIVE` lock.
- Bảng phình 67 lên 75 MB, `DROP COLUMN` không thu hồi lại được, phải `VACUUM FULL`
  thêm một lần khoá bảng nữa.
- Chậm hơn V3 mà đắt hơn nhiều về schema, và cũng chốt UTC nên lệch múi giờ giống V4.

Sau khi ước lượng đã đúng, planner bỏ hết index và chọn `Parallel Seq Scan`. Ép dùng
index bằng `enable_seqscan=off` cho 87,6 ms.

## Bẫy gặp trong lúc đo

Sau khi `VACUUM FULL orders` để thu hồi dung lượng, V2 mất hết tác dụng: plan rơi từ
`Index Only Scan` về `Bitmap Heap Scan` đọc đủ 8.604 block, thời gian gần bằng V1.

`VACUUM FULL` viết lại toàn bộ bảng và xoá sạch visibility map. Index Only Scan cần map
này để biết block nào đã all-visible, không có thì mọi dòng đều phải kiểm tra ở heap.

```
VACUUM (ANALYZE) orders;
SELECT relallvisible, relpages FROM pg_class WHERE relname='orders';   -->  8604 / 8604
```

![bẫy VACUUM FULL](../images/q3-vacuum-full-trap.png)

Chạy `VACUUM` thường xong thì Index Only Scan hoạt động lại. Kiểm tra `Heap Fetches`
trước khi kết luận một covering index là vô dụng.
